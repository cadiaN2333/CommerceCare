# 两型号比较实现与知识点

日期：2026-10-08。用户已授权直接写入，代码与项目测试完成；实测波动见[验证报告](../datasets/evaluation/routed-chat-v2/验证报告.md)。

## 代码阅读顺序

1. assistant/service/ComparisonTaskService.java：任务判断，仅在两个已知型号、有比较词和具体维度时比较。
2. assistant/service/ModelComparisonService.java：逐型号召回、预算、空侧短路、ID去重与污染检查。
3. assistant/service/RagChatService.java：chatWithEvidence与answerFromDocuments复用原生成，并按实际元数据构建EvidenceAnswer。
4. assistant/service/RoutedChatService.java：单型号、比较、澄清三条路径；识别MULTIPLE可以在明确任务与证据下回答。
5. assistant/dto/RoutedChatResponse.java：保留扁平sources，新增sourceGroups；集合深复制后只读。

这些文件均位于backend/src/main/java/com/lzq/commercecare下，类与关键流程已加中文注释。

## 知识点

### 识别状态与执行能力独立

MULTIPLE只表示提及多个型号，不必永远追问。任务是否明确、预算是否允许、证据是否覆盖，才决定能否比较。

### 候选完整不等于引用完整

先检索双方资料，生成后仍需检查双方都有引用。来源编号先验证，再映射实际候选；不能从标题或请求型号猜分组。

### 稳定去重不能隐藏冲突

同documentId且内容与元数据一致可去重；同ID内容或型号冲突时报错。score差异不作为资料内容冲突，保留首次候选顺序。

### 候选预算与返回数量分开

比较分支topK是每款候选数，最大3，总候选最多6。单型号原语义保留。输入与实际依赖返回数量都验证，不因上游超量而扩大上下文。

### 规则需要反例

不能用contains("不是")判断型号纠正，否则“是不是”也会被拦截。本次用明确的型号更正结构和回归测试收窄判断，仍不宣称通用语义理解。

### 测试通过不是生成稳定性保证

66项项目测试验证结构与规则，真实27题复测出现1条误拒。报告保留波动，下一阶段基于失败原因优化，而非修改标签追求满分。

## 调用示例

POST http://localhost:8081/api/v1/chat/routed：

```json
{
  "question": "SoundBee-A2和SoundBee-A2-Plus保修有什么区别？",
  "topK": 2
}
```

比较成功时strategy=MODEL_COMPARISON，识别仍是MULTIPLE，productModel仍为空。sources是扁平引用，sourceGroups分别展示两款；这与单型号的productModel含义不同。

版本化开发数据在datasets/evaluation/routed-chat-v2/cases.json。v1保留历史，不用旧澄清标签误判新能力。
