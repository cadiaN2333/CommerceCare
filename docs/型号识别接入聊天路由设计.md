# 型号识别接入聊天路由设计

日期：2026-10-08。状态：用户授权助手写入，项目代码与测试已验证；范围、隔离构建原因与日常服务待加载状态见[验证报告](../datasets/evaluation/routed-chat-v1/验证报告.md)。完整代码保留在[教程](型号识别接入聊天完整代码教程.md)。

## 1. 本阶段目标与边界

把已验证的型号识别结果用于真实聊天处理，建立“识别→澄清或型号过滤检索→有证据回答”的闭环。

新入口专用于需要具体型号的商品与售后咨询。通用物流、订单查询、无型号的通用FAQ还没有统一业务意图路由，不能据此把所有无型号请求都要求补型号或转人工。新入口的定位必须在API说明中明确。

保留原POST /api/v1/chat作为无过滤基线；新增POST /api/v1/chat/routed。首次沿用向量召回与原回答生成逻辑，不同时切换RRF、模型、重排或问题拆解。

这一小步是按型号识别状态分流，不是按问题复杂度选择RAG策略；尚不属于完整Adaptive-RAG、多Agent或有记忆的多轮客服。

## 2. 接入方案比较

| 方案 | 优点 | 代价 |
|---|---|---|
| 直接替换原chat | 单一入口 | 旧评测、旧客户端与无型号问题的语义会改变，基线难保留 |
| 新增routed入口 | 原有契约保留，同语料可做对照 | 暂时两入口，需要说明适用场景 |

推荐新增入口，验证效果与接口状态后，再考虑统一业务入口。

## 3. 确定性路由

| 型号识别状态 | 动作 | 聊天结果 | 检索/LLM |
|---|---|---|---|
| RESOLVED | 规范型号传入向量召回，原问题完整保留 | ANSWERED或INSUFFICIENT_EVIDENCE | 检索；有候选时生成 |
| MISSING | 提示补充完整型号并携带原问题 | NEEDS_CLARIFICATION | 不调用 |
| UNKNOWN | 提示核对完整型号，保留已知与未知提及 | NEEDS_CLARIFICATION | 不调用 |
| MULTIPLE | 保留全部型号，说明当前入口尚不能完成多型号比较 | NEEDS_CLARIFICATION | 不调用 |

只有RESOLVED可以把一个productModel传给检索。不能为UNKNOWN丢弃未知项，也不能为MULTIPLE选第一个型号。比较问题本身合理，当前是能力范围限制，不等于用户输入错误；后续可以独立增加比较路径。

没有候选直接返回INSUFFICIENT_EVIDENCE，不调用LLM。有相关候选但仍无法支撑核心问题时沿用当前结构化判断与来源编号校验，返回证据不足。

明确型号的候选还需服务端检查实际metadata.productModel一致；错型或缺型号候选不能进入上下文。发生这种不变量错误应报服务处理失败，不能静默放宽过滤或伪装成正常拒答。真实依赖故障仍按错误响应处理。

## 4. 接口契约

新入口沿用ChatRequest：question与topK，客户端不传productModel，不给客户端覆盖识别结果的机会。

新增独立RoutedChatResponse，原ChatResponse及其两种状态不变。

| 字段 | 含义 |
|---|---|
| status | ANSWERED、INSUFFICIENT_EVIDENCE、NEEDS_CLARIFICATION |
| strategy | MODEL_FILTERED_VECTOR或CLARIFY_MODEL，用于观察路径，不代表复杂度分类 |
| answer | 有证据答案、资料不足提示或澄清说明 |
| modelRecognition | 完整ModelRecognitionResponse，保留规范型号、未知项和原文提及 |
| sources | 复用ChatResponse.Source；澄清与证据不足时为空 |

HTTP200表示以上正常业务结果；空白问题、非法topK等仍为400；模型返回格式、来源编号或其他服务错误不能包成HTTP200“证据不足”。

识别到型号不代表订单已查询或售后资格已审核，原Prompt对假设条件的约束保留。

## 5. 模块与修改范围

- 新增assistant/dto/RoutedChatResponse.java：新入口的结果契约。
- 新增assistant/service/RoutedChatService.java：调用已有识别服务，选择澄清或调用RAG。
- 新增assistant/controller/RoutedChatController.java：只处理新入口，避免改变旧控制器构造与路径。
- 修改assistant/service/RagChatService.java：保留两参数chat方法，新增带可选规范型号的调用路径；复用生成、结构校验与来源整理逻辑。
- 新增路由测试及过滤RAG测试；不修改型号目录、识别正则、RRF算法或旧检索请求。

## 6. 澄清交互的限制

本阶段没有conversationId或会话状态，不能收到“是A2”就自动补到上一轮问题中。澄清说明应请用户将完整型号与原问题一起重新发送，例如“SoundBee-A2坏了能退吗？”。

不保存订单、身份或对话，不创建人工工单。MISSING状态不表示必须转人工。通用问题的分流与记忆补槽是后续独立阶段。

## 7. 验收与评测

### 单元测试必须验证

1. MISSING、UNKNOWN、MULTIPLE不会调用RagChatService。
2. RESOLVED传入原question、topK与规范大小写型号，不重写关键条件。
3. 路由正确映射RAG的回答与证据不足状态，保留识别详情。
4. 带型号RAG调用三参数检索，无候选不调用LLM。
5. 实际候选型号不符或缺字段时中止，不进入生成；不回退到无过滤。
6. 原两参数聊天仍是无过滤基线，旧接口结构不变。

### 接口与人工审核示例

| 问句 | 预期 |
|---|---|
| SoundBee-A2签收7天，未拆封配件齐全，可以退吗？ | 单型号检索；有依据时回答，不能声称已审核订单 |
| soundbee-a2-plus怎么重新配对？ | 归一成Plus型号，来源不得是A2 |
| SoundBee-A2支持哪些蓝牙编码格式？ | 型号已识别，但资料未提供，证据不足 |
| 耳机坏了能退吗？ | 澄清型号，来源为空 |
| SoundBee-Z9能换吗？ | 核对未知型号，不检索其他型号 |
| SoundBee-A2和SoundBee-A2-Plus保修有何区别？ | 保留两型号，提示当前单型号入口范围限制 |
| SoundBee-A2和SoundBee-Z9比较一下 | 不丢未知项，澄清 |

之后建立独立routed-chat开发集，包括可回答、已知型号无答案、缺失、未知、多型号与原条件边界；原检索保留验证问题不用于调路由。

自动检查路径、状态、规范型号、来源适用范围与空来源约束；答案是否覆盖全部要点仍需人工检查。记录检索、生成是否被调用及耗时，以证明澄清分支没有无效模型调用。

对同一开发问题集分别请求原chat与routed；澄清可作为正确业务结果，但不能当作问题已解决。分别统计正确回答、正确澄清、误拒答与错误回答，不把检索Recall当作端到端质量。
