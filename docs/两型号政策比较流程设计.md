# 两型号政策比较流程设计

日期：2026-10-08。状态：候选设计待用户确认，未修改业务代码。

## 1. 为什么进入这一阶段

日常8081复测结果位于artifacts/evaluation/routed-chat-20261008-194928-65076：新入口16条字段匹配、7回答、2证据不足、7澄清；原chat在9条可同标签检查问题中8条匹配。

原chat能回答已有两型号保修比较，新入口却因MULTIPLE固定澄清。下一步扩大这一合理任务的支持范围，让单型号与两型号比较分别走可观察路径。

这仍是按任务类型分流与并列证据收集。订单事实影响下一步政策选择的依赖式多跳，以及复杂度Adaptive路由和多Agent，留在后续阶段；不能把比较两个独立型号宣称为已解决全部多跳。

## 2. 范围与备选路线

| 路线 | 能力与代价 |
|---|---|
| 全库一次检索后比较 | 实现改动少，但候选可能集中在其中一款，难保证两边都有资料 |
| 分型号过滤检索，再合并生成 | 推荐；每款独立取证，可核验覆盖，两次检索增加一定开销 |
| 自主多Agent比较 | 适合更广的工具与任务选择；当前这一步可以由确定性服务完成 |

首版只接受两个已知不同型号、明确比较词与明确比较维度。支持现有资料中的退换、保修/维修、发票、配送、配对、充电等维度。没有具体维度时先询问比较哪方面；三个及以上型号暂提示缩小范围。

“哪个更好、更值得买”不能凭售后期限推断性能或性价比。相关维度没有知识时应证据不足，而非凭模型常识补参数、价格或推荐。

## 3. 路由规则

规则目录沿用已有识别服务，不改规范型号或别名支持范围。

| 条件 | 路径 |
|---|---|
| RESOLVED | 原MODEL_FILTERED_VECTOR |
| UNKNOWN或MISSING | 原CLARIFY_MODEL |
| MULTIPLE且恰好2个已知型号、明确比较、维度明确 | 新MODEL_COMPARISON |
| 多型号但无明确比较任务/维度、明显纠正语句或超过2款 | 澄清任务范围，不默认选一个 |

明确比较词首版从“区别、差别、比较、对比、哪个/哪款”识别；明确维度从既有资料主题维护小型业务词表。明显纠正表达例如“不是……而是……、说错、改成”出现时保守澄清，不把型号更正当成比较。这些规则是限定范围的初版，需评测漏判，不宣称通用意图识别。

ModelRecognitionResponse仍然保留MULTIPLE与productModel=null；是否能回答由任务路由与证据决定，不把多型号状态改造成RESOLVED。

## 4. 有界比较工作流

1. 保留原问题与两个规范型号的首次出现顺序。
2. 每个型号调用原向量检索的精确过滤路径，原问题不改写。
3. 比较分支每款取min(topK,3)个候选，最多合并6片段；单型号topK语义保持原样。两次检索先顺序执行，记录开销再评估并行或Embedding复用。
4. 校验每条候选确属于其检索型号，错型或缺型号视为服务错误，不静默丢弃或扩大搜索范围。
5. 任一型号没有候选，直接证据不足，不生成只有一侧的比较。
6. 按documentId去重；重复ID却指向不同型号等冲突元数据时中止，不能任选一条。
7. 合并后只生成一次，要求明确区分两款事实，问题维度无证据则返回证据不足。
8. 沿用来源编号校验；若模型声明可回答但引用没有覆盖两款，视为生成结果无效，不伪装为正常“没有资料”。本阶段不自动重试。

两侧有候选、两侧有引用都不保证比较结论正确。最终是否覆盖问题及是否存在无依据推断，还需逐条答案审核。

## 5. 接口与来源展示

继续使用POST /api/v1/chat/routed，请求仍为question和topK，原chat基线不变。

- strategy新增MODEL_COMPARISON，原状态ANSWERED、INSUFFICIENT_EVIDENCE、NEEDS_CLARIFICATION保留。
- sources保留原扁平结构，新增sourceGroups按规范型号展示引用。
- sourceGroups的型号归属来自实际候选元数据与已校验的来源编号，不从sourceId或标题猜测；非回答结果为空。
- 单型号回答也能形成一个来源分组；比较答案必须有两组有效引用。
- modelRecognition保留两款提及、MULTIPLE状态和未知项说明，客户端不能另传型号覆盖服务端判断。

原v1用例RC-012的澄清预期是当时的范围限制。升级后该题应回答比较，须新增v2评测标签并保留v1历史，不能悄悄改旧报告或宣称旧基线退步。

## 6. 模块职责

- 新增小型任务判断服务：输出单型号/明确比较/澄清，不调用LLM。
- 新增比较服务：逐型号召回、预算、覆盖与元数据检查、合并与引用分组。
- RagChatService提取内部共享的“给定证据生成答案”方法，保留原入口及来源编号规则；比较服务在完成候选验证后调用，不复制两套生成逻辑。
- RoutedChatService按任务调用已有单型号路径或比较路径。
- RoutedChatResponse增加分组字段与比较策略，旧chat DTO不改。

不在本阶段接入RRF、Rerank、Graph、自主Agent、会话或订单工具，避免无法归因改动收益。

## 7. 测试与评测

单元测试覆盖：两型号比较的触发与否、未知优先、纠正句不误入比较、每款参数与预算、任一侧空结果、错型元数据、稳定去重、冲突ID、引用覆盖两款、单型号兼容。

新增独立比较开发集与routed-chat-v2定义，包括：保修差异、不同退货期限、配对时长差异、比较维度缺失、两型号未知价格/参数、三型号超预算、纠正语句、同型号重复提及。

同集比较三种路径：原无过滤chat、当前单型号routed历史表现、新比较分支。分别报告两侧证据覆盖、答案事实与引用、正确澄清/拒答、请求错误和延迟；不把接口正常、澄清或字段匹配当作解决率。
